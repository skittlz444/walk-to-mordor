## 4. Progress Reconciliation

- [ ] 4.1 Implement the event progress reconciliation service in `src/event-utils.ts`: given a participant and a source progress entry, check if `progress.date` falls within `[started_at, coverage_end_date]`. If eligible, upsert or delete a ledger row with `UNIQUE(participant_id, source_progress_id)`, then recompute `event_participants.progress_distance = SUM(ledger.distance)`. Wrap in try/catch — errors are logged but NEVER propagated (graceful degradation, matching the `syncPartyProgressLog` pattern).
- [ ] 4.2 Implement the completion check helper: after reconciliation, if `progress_distance >= personalized_target`, mark the occurrence completed and call `awardAchievement` with the `encounter_occurrence:<occurrence_id>` idempotency key. There is no all-coverage-days precondition (a target reached on day 1 completes the challenge).
- [ ] 4.3 Hook reconciliation into progress create: after a new progress row is inserted in `src/progress-handlers.ts` (following the `syncPartyProgressLog` call), find all active personal challenge participants for that user, and for each, reconcile if the progress date is within the coverage window, then check completion.
- [ ] 4.4 Hook reconciliation into progress update: after an existing progress row is edited, reconcile the ledger entry for that (participant, progress_id) combination if the date is within any active challenge's coverage window, then check completion.
- [ ] 4.5 Hook reconciliation into progress delete: capture the progress row id before deletion in `src/progress-handlers.ts` (the current delete path removes by `(date, user_id)` without selecting the id), then remove the corresponding ledger entries by `source_progress_id`, recompute cached totals, and never revoke an earned badge.
- [ ] 4.6 Add Jest coverage for: coverage-window-eligible walk credit, coverage-window-ineligible walk exclusion, grace-period credit for window dates, grace-period exclusion for non-window dates, completion on day 1 (total ≥ target), total below target stays active, later-edit completion, ledger idempotency, delete-hook credit removal, graceful error handling (walk save succeeds despite reconciliation failure), and badge preserved after progress reduction.
