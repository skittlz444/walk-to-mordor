Handlers rely on the `adminGuard` middleware (no per-handler session validation), read `adminUserId` from context, operate on `campaign_definitions` and `campaign_runs`, manage the linked badge definition in `achievement_definitions` (auto-create on save from inline badge fields including `is_repeatable` and `metadata.rank_thresholds`; only update rows with `badge_type='community'`), handle `campaign_participants.status` for disable, log via `logAdminAction` from `admin-shared.ts`, and return JSON responses.
- [x] 1.2 Implement validation for campaign fields: slug (required, max 80, kebab-case, unique), name (required, max 120), description (required, max 2000), image_slug (required, max 120), badge_slug (required, max 120), target_distance (required, number > 0), start_date (required, ISO date, >= today UTC on create only; not re-validated on update while upcoming), end_date (required, ISO date, > start_date). Freeze the active run's target_distance and start_date plus the campaign's badge_slug once status is not `upcoming`; allow end_date extension only. Validate badge_slug against `achievement_definitions` — if no match but inline badge fields (badge_name, badge_description, badge_image_slug, repeatable, rank_thresholds) are provided, auto-create the achievement definition row; never update a non-community badge type. Return `{ error: "validation", fields: { ... } }` on failure.
- [x] 1.3 Implement community metric suggestions: query total distance and distinct active user count from `progress` table for the past 30 days. Return suggested target distance = `total / max(activeUsers, 1) * durationDays * 0.25` rounded to the nearest km, suggested duration days (requested `durationDays`, default 14, clamped 7–30), suggested participant count, and raw totals.
- [x] 1.4 Implement disable-with-confirmation: `PUT /api/admin/campaigns/:id/disable` checks for `campaign_participants` rows with `status = 'active'`. If any exist, returns `{ activeParticipants: N, requiresConfirmation: true }` (400 status). Client must re-send with `{ cancelActive: true }` or `{ cancelActive: false }`. `true` marks active participants `status='removed'` with `removed_at = now()` and keeps ledger rows and earned badges; `false` leaves participant rows untouched. Either way the campaign is frozen (`enabled = 0`). Audit log records participant count when cancelled. `PUT .../enable` sets `enabled = 1` and runs the campaign backfill for active participants.
- [x] 1.5 Implement retrigger: `POST /api/admin/campaigns/:id/retrigger` requires the latest run to be `completed` or `expired` and the campaign to be enabled (400 otherwise). Pre-fills target from the suggestions formula (clamped to >= 1 km), `start_date` default tomorrow UTC (>= today), `end_date` default `start_date + 13` (14-day inclusive window); the request body may override `target_distance`, `start_date`, `end_date` with the same validation rules. Inserts the next `campaign_runs` row (`run_number` = max+1, `status = 'upcoming'`, `announced_at = NULL`) in one D1 batch that also writes the audit entry; never modifies or deletes previous runs, participant rows, or ledger entries. When the `community-campaign-notifications` change is applied, dispatches the run-announcement notification from this route via the route-layer background scheduling callback.
