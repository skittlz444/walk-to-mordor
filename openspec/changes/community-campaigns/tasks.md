## 4. Progress Reconciliation

- [x] 4.1 Implement run progress reconciliation service in `src/campaign-utils.ts`: resolve the user's participations in runs with `status = 'active'`, skip disabled campaigns, then check if `progress.date >= run.start_date AND progress.date <= run.end_date`. If eligible, upsert or delete a ledger row with `UNIQUE(participant_id, source_progress_id)`, then recompute `campaign_participants.progress_distance = SUM(ledger.distance)`. Skip participants with `status = 'removed'`. Wrap in try/catch — errors are logged but NEVER propagated (graceful degradation, matching the `syncPartyProgressLog` pattern).
- [x] 4.2 Implement run completion check during reconciliation: after updating participant totals for a run, compute the scoped total `SUM(campaign_progress_ledger.distance)` joined through the run's active participants. If the total meets or exceeds `campaign_runs.target_distance`, mark the run completed via a guarded UPDATE (`WHERE ... AND status = 'active'`, proceeding only when `changes > 0`), write the final snapshot (participant count, contributor count, total), and call `awardAchievement` (idempotency key `campaign:<slug>:run:<run_id>`) for all active participants with `progress_distance > 0`. The status guard matches the personal-challenges completion pattern (`src/event-utils.ts`) and prevents future-dated walks from completing an upcoming run or a backdated walk from completing an expired one.
- [x] 4.3 Hook reconciliation into progress create in `src/progress-handlers.ts`: after a new progress row is inserted (following the existing `syncPartyProgressLog` call), find all active-run participants for that user, and for each, reconcile if the progress date is within the run window, then check for run completion.
- [x] 4.4 Hook reconciliation into progress update: before the UPDATE, fetch the existing row's distance (`SELECT distance FROM progress WHERE date = ? AND user_id = ?`) — this is one additional query. After the UPDATE succeeds, pass both old and new distances to the reconciliation service so it can correctly UPDATE (not duplicate) the ledger entry. Then check completion.
- [x] 4.5 Hook reconciliation into progress delete: after a progress row is deleted, remove the corresponding ledger entries and recompute cached totals. Never revoke an earned badge; ledger deletion is limited to the deleted walk's own row, never to run history.
- [x] 4.6 Add Jest coverage for: walk-date-within-window credit, walk-date-outside-window exclusion, status gating (upcoming/completed/expired runs neither credit nor complete, including future-dated walks), join-time backfill of existing in-window walks, join backfill idempotency, edited walk reconciliation (old → new, no duplicate ledger row), deleted walk reconciliation, ledger idempotency, run completion detection during reconciliation with guarded UPDATE, final snapshot written once, badge awards to all active contributors with the per-run key, repeatable badge re-award under a different run key, removed participants excluded from reconciliation and ranking, disabled campaigns skipped, graceful error handling (walk save succeeds despite reconciliation failure).
